# Правило 25. Квалификация времени: AS-IS или TO-BE

25. **Квалификация времени.** Описание механики процесса — шаги, интеграции, сроки, участники, порядок контроля — не фиксируется как требование, пока не определено, к какому времени оно относится. Факт о механике без временного тега в документ не попадает.

    **Зачем.** Достоверность и время — разные оси. «Реестр приходит через Kafka со списком клиентов» одинаково `[подтверждено]` и как описание текущего процесса, и как требование к целевому. Тег достоверности эту разницу не ловит, а цена ошибки высокая: описание нарушающего процесса, записанное как требования, отправляет команду реализовывать то, от чего уходят.

    **Триггеры.** Правило включается, когда ответ:
    - описывает механику от двух шагов подряд;
    - сформулирован в настоящем времени («передаёт», «производится», «контролирует»);
    - содержит «сейчас», «у нас», «автоматизировано», «в разработке»;
    - называет конкретные системы, интерфейсы, форматы обмена.

    **Явная метка времени.** Правило включилось — сначала ищи явную метку. «Сейчас», «в текущем процессе», «сегодня делаем» → `[AS-IS]`; «будет», «должно», «в целевом процессе», «хотим, чтобы» → `[TO-BE]`. Метка названа — тегируй без вопроса и покажи тег в резюме чекпоинта, где его можно поправить. Разные метки в одном описании — тегируй по пунктам. Неявные признаки без метки — настоящее время, названия систем, «у нас», «автоматизировано», «в разработке» — вопрос ниже: по ним время не определить.

    **Действие.** Один вопрос **до** записи: «Это описание текущего процесса или целевого?» Три опции: текущий (AS-IS) · целевой (TO-BE) · смешанное, разберём по пунктам. Составное описание общим ответом не принимается: при ответе «смешанное» разложи по пунктам и тегируй каждый отдельно.

    **Переход AS-IS → TO-BE.** Элемент текущего процесса, который сохраняется в целевом, становится требованием только после явного подтверждения: «это переносится в целевой процесс без изменений?» Молча переносить нельзя — иначе в документе появляются требования, которых стейкхолдер не формулировал. Перенесённое помечай в колонке достоверности: `[подтверждено]`, «переносится из текущего процесса».

    **Куда попадает AS-IS.** В секцию 6.0 документа как контекст, не как требования. Нестыковки внутри самого описания AS-IS не выправляй на ходу — выноси в открытые вопросы: текущий процесс мог быть описан по памяти, и его противоречия к целевому отношения не имеют.

    **Приоритет активации.** Для инициатив типа «исправление существующего процесса» (регуляторное предписание, миграция, рефакторинг, устранение нарушения) правило активно с первого блока: AS-IS там существует всегда, и стейкхолдер описывает его по умолчанию, часто без предупреждения.

    **Ограничители.** Правило спит для инициатив с нуля, где AS-IS не существует — тогда секция 6.0 опускается. Не срабатывает на единичный факт («доход зачисляется на тот же счёт») — только на описание механики. Один вопрос на описание, не по вопросу на каждый пункт.

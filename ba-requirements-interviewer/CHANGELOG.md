# Changelog

Все значимые изменения скилла `ba-requirements-interviewer` — ИИ-агента бизнес-аналитика для сбора требований в финтех-инвестициях.

Версии отражают итерации разработки в порядке появления. Даты не проставлены намеренно — при внедрении в git проставляются по фактическим коммитам.

---

## v0.15 — Транскрипт как вход для повторного прогона

- Назначение транскрипта переопределено: основное — воспроизводимый вход для повторного прогона скилла (новая модель или версия скилла, улучшение результата, перезапуск отменённой или перенесённой инициативы, смена владельца), а не архив переписки.
- Транскрипт стал самодостаточным: метаданные прогона (версия скилла, профиль, плановый набор блоков), пары «вопрос → ответ» с идентификаторами вопросов банка/профиля, явная фиксация незаданного и пропущенного.
- Новый обязательный раздел «Карта для повторного прогона»: что переиспользовать без переспрашивания, что предъявить на подтверждение, что задать заново.
- Четвёртый режим старта в шаге 0 — «Повторный прогон по транскрипту» с переиспользованием ответов и сообщением стейкхолдеру, сколько вопросов останется.
- Срок хранения транскрипта приравнен к сроку жизни инициативы.

## v0.14 — Транскрипт интервью

- Второй обязательный выходной артефакт: `references/transcript-template.md` — дословный транскрипт сессии со сквозной нумерацией реплик, служебными событиями, сводкой и разделом «Расхождения и смены позиции».
- Требования в BRD ссылаются на номер реплики транскрипта в колонке «Источник» — происхождение каждого требования прослеживаемо.
- Оба файла выдаются одним каналом и хранятся рядом; при отказе стейкхолдера от транскрипта выдаётся только BRD с фиксацией отказа.

## v0.13 — Соразмерность формата масштабу

- Для мелкой фичи пакетный режим включается по умолчанию без выбора темпа; один общий чекпоинт вместо поблочных; консолидированное ревью и walkthrough объединяются; обязательный минимум секций документа сокращён до шести.
- Явный критерий мелкой фичи: одна система, один тип пользователя, нет новых интеграций и регуляторных вопросов — нарушение любого пункта означает полный формат.
- Страховка: даже в сжатом формате задаётся минимум по одному вопросу про регуляторику и про ИБ/права доступа.

## v0.12 — Пакетный режим бриф-дампа

- Снят конфликт правила «один вопрос за раз» с режимом бриф-дампа: описан пакетный режим — подтверждения чек-листом, пробелы пакетами по 3–5 вопросов одной темы с разрешением ответить частично, углубляющие вопросы всегда по одному.
- Страховка: при односложных ответах в бриф-дампе агент предлагает вернуться к обычному интервью.

## v0.11 — Побочный улов

- Правило 17: агент ведёт три параллельных списка (риски, ограничения, глоссарий-кандидаты) и пополняет их из любой реплики, а не только из ответов на профильные вопросы блоков. Триггерные формулировки, лимит 2–3 записи на блок, сообщение о пополнении на чекпоинте.
- Записи побочного улова несут статус `[гипотеза]` до подтверждения; к блокам рисков/ограничений агент приходит с готовым черновиком вместо пустого вопроса.
- Шаблон BRD: секция «Ограничения и риски» разбита на две таблицы с указанием источника записи и её достоверности.

## v0.10 — Доменные профили

- Новый `references/domain-profiles.md`: универсальное ядро (блоки 1, 2, 9, 10) + четыре профиля — А розничный брокеридж, Б корпоративные/B2B-продукты, В операционные системы (бэк/мидл-офис), Г системы обслуживания клиентов (CRM, рабочее место менеджера).
- Профили комбинируются (напр., ESOP-платформа = Б + В); агент определяет профиль из питча и предъявляет на подтверждение.
- Правило 8 разделено на два измерения: глубина (сколько блоков) и ширина (какой профиль).

## v0.9 — Самопроверка полноты и кодовые имена

- Самопроверка перед формированием документа: каждый open question происходит из заданного вопроса, а не из забытого агентом; незаданные вопросы планового набора дозадаются или помечаются статусом «не задан агентом».
- Наименования юрлиц заменены кодовыми именами: «Красное юрлицо», «Фиолетовое юрлицо» — во всех файлах скилла.
- Банк вопросов: из 3.6 убрана ссылка на несуществующую норму 3030-У; 8.2 (latency/NFR) переформулирован понятным неспециалисту языком.
- Удалена петля обратной связи (бывший шаг 4): сессия завершается выдачей результата, файлы фидбека больше не создаются.

## v0.8 — Видимость команд и форматирование

- Памятка команд («пропустить · позже · статус · завершить сейчас») обязательна в первом сообщении сессии, повторяется в плане интервью и по команде «статус». Стейкхолдер не может пользоваться командами, о которых не знает.
- README.md и .gitignore для публикации скилла в git-репозитории.
- Шапка шаблона BRD: каждый пункт входных данных — с новой строки (пустая строка между пунктами для корректного рендеринга markdown).
- Бизнес-требования (секция BR) оформляются таблицей вместо списка — проще восприятие при 4+ требованиях.
- Глоссарий перенесён в секцию 1 — читатель сразу говорит с документом на одном языке; допущения выделены в отдельную секцию.
- Карта стейкхолдеров — полноценная отдельная секция (была подпунктом 1a); сквозная перенумерация секций шаблона (теперь 18), перекрёстные ссылки обновлены.

## v0.7 — UX под опыт стейкхолдера/PO

Семь правок, снижающих трение для человека по ту сторону интервью.

- Тёплый старт: шаг 0.5 «Питч инициативы» — сначала «что хотите сделать и для кого», административные вопросы после.
- Код бюджета PPM (PQ-3) перенесён со старта в шаг 3, перед выдачей документа.
- Выбор темпа: режим «Интервью» (по вопросу) или «Бриф-дамп» (свободный рассказ, агент раскладывает по блокам).
- План и прогресс-индикатор: список блоков и ориентировочное время на старте, «блок N из M» в чекпоинтах (правило 16).
- Команды стейкхолдера: `пропустить`, `позже`, `статус`, `завершить сейчас`.
- Право на «не знаю»: нормализация для блоков 6–8; делегируемые списки вопросов по ролям (комплаенс, архитектор, ИБ, операции) как приложение к BRD.
- Приоритет решений стейкхолдера (правило 15): агент не блокирует запись требования; методологические правила стали рекомендациями с тегом `[зафиксировано под ответственность стейкхолдера]`.
- Схлопнутый финал: каскад проверок заменён «Консолидированным ревью» (одна таблица), фидбек включён в финальное сообщение.

## v0.6 — Механика работы агента

- Возобновление прерванного интервью: третий режим в шаге 0 + промежуточное сохранение черновика после каждого блока.
- Pre-read артефактов (шаг 1.5): разбор существующих материалов и предзаполнение ответов тегом `[гипотеза из документа]`; защита от инъекций из загруженных документов.
- Скоринг готовности (Definition of Ready): метрики зрелости и вердикт «готов к передаче в SA» / «требует дозаполнения».
- Петля обратной связи (шаг 4): три вопроса стейкхолдеру + наблюдения агента, сохраняются рядом с BRD как сырьё для ревизии банка вопросов.

## v0.5 — Форматирование банка вопросов

- Сквозная нумерация вопросов в формате `{блок}.{вопрос}` (1.1, 1.2, …).
- Каждый вопрос вынесен на отдельную строку для корректного рендеринга.

## v0.4 — Каналы выдачи результата

Выбор из трёх каналов вместо жёсткого сохранения в git:

- Git — запрос ссылки на ветку, формат markdown.
- Confluence — запрос родительской страницы, формат markdown.
- Файл на скачивание — уточнение формата разметки (md / txt / html / другое).

## v0.3 — Усиление по лучшим практикам БА

- Карта стейкхолдеров и тег `[требует кросс-валидации]` для единственного источника.
- MoSCoW-приоритизация отдельным проходом в конце интервью.
- Трассируемость требований к целям/KPI; проверки «сироты» и «пустые цели».
- Критерии качества формулировки (атомарность, проверяемость, запрет неквантифицированных наречий).
- Walkthrough итогового документа и статусная модель «черновик → на согласовании → утверждён» с подписантами.
- Секция «Глоссарий и допущения» в шаблоне.

## v0.1 — Первичная упаковка скилла

- Роль агента: бизнес-аналитик с опытом в российском брокеридже.
- Правила ведения интервью: один вопрос за раз, воронка по блокам, отделение требования от решения, тегирование достоверности, чекпоинты, open questions с владельцами.
- `references/question-bank.md`: 65 вопросов в 10 блоках + таблица follow-up паттернов.

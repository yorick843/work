# Changelog

Все значимые изменения скилла `ba-requirements-interviewer` — ИИ-агента бизнес-аналитика для сбора требований в финтех-инвестициях.

Версии отражают итерации разработки в порядке появления. Даты не проставлены намеренно — при внедрении в git проставляются по фактическим коммитам.

---

## v0.23 — Оптимизация и устранение противоречий

Ревизия SKILL.md: объём сокращён с 56 КБ до 37 КБ (−34%) без потери смысла.

Устранённые противоречия:
- Ресурсы ссылались на «65 вопросов в 10 блоках» — актуализировано до 81 вопроса в 11 блоках.
- Правило «один вопрос за раз» знало только про исключение для бриф-дампа, но не для мелкой фичи (где пакетный режим включается по умолчанию).
- Правило «побочный улов» объявляло три списка, а перечисляло четыре.
- Правило качества формулировки запрещало неквантифицированные наречия, что конфликтовало с правилом приоритета решений стейкхолдера («никогда не отказывайся записать требование»). Теперь: записывать как сказано + open question на уточнение.
- Правило чекпоинтов требовало резюме после каждого блока без оговорки про мелкую фичу, где чекпоинт один.
- Вопрос о режиме работы перечислял три варианта при четырёх опциях.
- Промежуточное сохранение было неоперациональным («при любом признаке скорого завершения») — заменено на выдачу черновика после каждого второго блока со строкой `resume-point`.
- Самопроверка полноты сверялась только с банком, игнорируя вопросы доменного профиля.
- Флаги консолидированного ревью не включали «метрику без поддерживающего требования».
- Описание скилла упоминало два режима из четырёх и один выходной артефакт из двух.
- Дублирование глоссария между отдельным правилом и списком побочного улова.
- Порядок блоков в правиле воронки не включал блок «Интерфейс и представление».

Структурные улучшения: правила сгруппированы по темам (диалог / фиксация / сбор и полнота / ритм сессии), ресурсы вынесены в таблицу, добавлена сводка структуры банка вопросов, убраны риторические пояснения. Правил стало 22 (было 20 с дублями), перекрёстные ссылки пересчитаны.

## v0.22 — Мягкий заход в технические блоки

- Обязательный дисклеймер перед блоками интеграций и NFR: технических знаний не требуется, незнание — нормальное разделение труда, а не пробел; всё неотвеченное адресуется архитектору и ИБ.
- Вопросы блока 9 (NFR) переформулированы в терминах пользовательского опыта и бизнес-последствий вместо архитектурных: нагрузка — «сколько людей и бывают ли наплывы», доступность — «когда система обязана работать без перерыва», деградация — «что клиенту хуже: устаревшее или ничего», ИБ — «насколько чувствительны операции», наблюдаемость — «о чём вы обязаны узнать не от клиента».
- Технические уточнения (протоколы, инфраструктура, конкретные метрики) стейкхолдеру не задаются вовсе — сразу в делегируемый список для архитектора.

## v0.18 — Два типа критериев успеха

- Правило 20: критерии успеха классифицируются на критерии качества запуска (технические, бинарные) и критерии достижения цели (продуктовые метрики). Подмена второго первым отлавливается в момент ответа, а не на финальном ревью.
- Агент предлагает ориентиры по типу инициативы и не передавливает: для инфраструктурных задач фиксируется «влияние косвенное, не измеряется» вместо выдуманной метрики.
- Новый вопрос 10.3 в банке и follow-up паттерн на «запуск без инцидентов».
- Шаблон BRD: секция критериев приёмки разделена на два подраздела; в трассировочные проверки добавлен третий тип разрыва — метрика без поддерживающего требования.

## v0.17 — Сверка ответов с вопросами

- Правило 19: при нескольких заданных вопросах агент сопоставляет ответы с вопросами по смыслу, а не по нумерации стейкхолдера; несопоставленное фиксируется немедленно.
- Реакция по важности вопроса: влияющий на scope возвращается первым в следующий пакет, остальное сразу уходит в open questions одной нейтральной строкой; один вопрос не переспрашивается дважды.
- Механика распространена на бриф-дамп и pre-read: агент явно отмечает, что из планового набора материалы не покрыли.
- Самопроверка полноты понижена до финальной страховки — основной барьер теперь работает сразу после пакета.

## v0.16 — Проверка внешних утверждений

- Правило 18: утверждения о внешней стороне (права на данные и товарные знаки, ссылки на нормы, публичные условия поставщиков, ограничения внешних API) проверяются по первоисточникам. Внутренние факты компании и продуктовые решения не проверяются.
- Проверки выполняются пакетом перед консолидированным ревью, а не на лету — темп интервью не ломается; результаты предъявляются, пока стейкхолдер в сессии.
- Расхождение оформляется тремя элементами (ссылка на первоисточник, суть условия, задача для профильной роли) с запретом на юридическую квалификацию со стороны агента; при влиянии на возможность выпуска становится блокирующим open question.
- Ограничители: 3–5 проверок за сессию, только первичные источники, при неоднозначном результате агент не додумывает.

## v0.15 — Транскрипт как вход для повторного прогона

- Назначение транскрипта переопределено: основное — воспроизводимый вход для повторного прогона скилла (новая модель или версия скилла, улучшение результата, перезапуск отменённой или перенесённой инициативы, смена владельца), а не архив переписки.
- Транскрипт стал самодостаточным: метаданные прогона (версия скилла, профиль, плановый набор блоков), пары «вопрос → ответ» с идентификаторами вопросов банка/профиля, явная фиксация незаданного и пропущенного.
- Новый обязательный раздел «Карта для повторного прогона»: что переиспользовать без переспрашивания, что предъявить на подтверждение, что задать заново.
- Четвёртый режим старта в шаге 0 — «Повторный прогон по транскрипту» с переиспользованием ответов и сообщением стейкхолдеру, сколько вопросов останется.
- Срок хранения транскрипта приравнен к сроку жизни инициативы.

## v0.14 — Транскрипт интервью

## v0.13 — Соразмерность формата масштабу

- Для мелкой фичи пакетный режим включается по умолчанию без выбора темпа; один общий чекпоинт вместо поблочных; консолидированное ревью и walkthrough объединяются; обязательный минимум секций документа сокращён до шести.
- Явный критерий мелкой фичи: одна система, один тип пользователя, нет новых интеграций и регуляторных вопросов — нарушение любого пункта означает полный формат.
- Страховка: даже в сжатом формате задаётся минимум по одному вопросу про регуляторику и про ИБ/права доступа.

## v0.12 — Пакетный режим бриф-дампа

- Снят конфликт правила «один вопрос за раз» с режимом бриф-дампа: описан пакетный режим — подтверждения чек-листом, пробелы пакетами по 3–5 вопросов одной темы с разрешением ответить частично, углубляющие вопросы всегда по одному.
- Страховка: при односложных ответах в бриф-дампе агент предлагает вернуться к обычному интервью.

## v0.11 — Побочный улов

- Правило 17: агент ведёт три параллельных списка (риски, ограничения, глоссарий-кандидаты) и пополняет их из любой реплики, а не только из ответов на профильные вопросы блоков. Триггерные формулировки, лимит 2–3 записи на блок, сообщение о пополнении на чекпоинте.
- Записи побочного улова несут статус `[гипотеза]` до подтверждения; к блокам рисков/ограничений агент приходит с готовым черновиком вместо пустого вопроса.
- Шаблон BRD: секция «Ограничения и риски» разбита на две таблицы с указанием источника записи и её достоверности.

## v0.10 — Доменные профили

- Новый `references/domain-profiles.md`: универсальное ядро (блоки 1, 2, 9, 10) + четыре профиля — А розничный брокеридж, Б корпоративные/B2B-продукты, В операционные системы (бэк/мидл-офис), Г системы обслуживания клиентов (CRM, рабочее место менеджера).

- Правило 8 разделено на два измерения: глубина (сколько блоков) и ширина (какой профиль).

- Удалена петля обратной связи (бывший шаг 4): сессия завершается выдачей результата, файлы фидбека больше не создаются.

## v0.8 — Видимость команд и форматирование

- Памятка команд («пропустить · позже · статус · завершить сейчас») обязательна в первом сообщении сессии, повторяется в плане интервью и по команде «статус». Стейкхолдер не может пользоваться командами, о которых не знает.
- README.md и .gitignore для публикации скилла в git-репозитории.
- Шапка шаблона BRD: каждый пункт входных данных — с новой строки (пустая строка между пунктами для корректного рендеринга markdown).
- Бизнес-требования (секция BR) оформляются таблицей вместо списка — проще восприятие при 4+ требованиях.
- Глоссарий перенесён в секцию 1 — читатель сразу говорит с документом на одном языке; допущения выделены в отдельную секцию.
- Карта стейкхолдеров — полноценная отдельная секция (была подпунктом 1a); сквозная перенумерация секций шаблона (теперь 18), перекрёстные ссылки обновлены.

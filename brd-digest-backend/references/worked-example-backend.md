# Выжимка для бекового аналитика: перераспределение партнёрского кешбэка

**BRD:** v1.0 от 15.01.2030 · **Статус:** требует дозаполнения (7 блокирующих OQ) · **Читатель:** backend (БА+СА), бековый тестировщик
**Охват:** 74 ID в BRD, все учтены (проверено `scripts/brd_tools.py coverage`): в разделах A–G, в «Стыках» или в «Опущено»

## 1. Суть доработки

Процесс перераспределения кешбэка по офферам, которые клиенты подключили через партнёра-агрегатора, построен на неверной логике: позиция партнёра в реестре подменяется позициями клиентов. Нужно строить реестр по фактическому балансу партнёра на конец расчётной даты, выплачивать кешбэк на счёт партнёра, а затем автоматически перераспределять его клиентам — участникам акции. Срок — 01.07.2030 (новая редакция оферты программы лояльности).

## 2. Бизнес-смысл

Приведение процесса к новой редакции оферты; отдельной продуктовой метрики нет. Последствие бездействия — расхождение с офертой. После запуска операционный контроль проверяет каждый реестр перераспределения. Приоритеты: Must — контур оферты, Should — контроль, Could — отчёт в BI.

## 3. Бизнес-процессы

| Было (AS-IS) | Станет (TO-BE) |
|---|---|
| Расчётный центр передаёт брокеру реестр выплат через очередь сообщений (JSON); позиция партнёра заменена позициями клиентов; выплата и сбор идут сразу конечным получателям | Реестр строится по балансу на бонусном счёте партнёра (BR-01); выплата идёт на счёт партнёра (BR-02); расчётный центр определяет конечных получателей (BR-25) и с кого удерживать сбор (BR-26); брокер сверяет поступление и автоматически перераспределяет (BR-27, BR-11) |

Участники и системы: ИТ расчётного центра (реестр, получатели, выплата, сбор по денежному кешбэку); ИТ брокера (приём реестра, сверка, перераспределение, Back Office, BI); ИТ-сопровождение (корректировки); операционный контроль (контроль); партнёр (получатель кешбэка, без доработок).

### D. Статусы и переходы

Жизненный цикл реестра в BRD не описан. Из условий следуют переходы `[выведено: BR-27, BR-11]`:

| Из | Условие | В |
|---|---|---|
| реестр получен | поступление суммы подтверждено по этому реестру (BR-27) | перераспределение запускается автоматически (BR-11) |
| реестр получен | сумма не совпала | не определено — OQ-18 |
| перераспределено | ошибка найдена внутри операционного дня | корректировка по BR-30 (NFR-01) |
| перераспределено | ошибка найдена позже | корректировка задним числом по BR-35 |

`[пробел]`: перечень состояний реестра и операции, признаки «остановлено» и «перезапущено» (BR-12).

### 7.2 Граничные случаи

| ID | Граница | Что проверить |
|---|---|---|
| BR-03 | расчётная дата в день входа и в день выхода | интервал включает вход и исключает выход |
| BR-32 | остаток округления, один получатель | остаток всё равно на последней записи |
| BR-27 | сумма меньше, больше и равна ожидаемой | поведение определено только для «равна»; остальное — OQ-18 |
| BR-20 | получение реестра перед закрытием дня | всё в один операционный день `[выведено]` |
| BR-10 | счёт закрыт | сценарий не определён (R-10) |

### 7.3 Тестовые данные

Клиенты: физлица и юрлица, резиденты и нерезиденты, совместный и личный счёт (BR-05, BR-10); типы кешбэка: денежный кешбэк, бонусы за пополнение, приветственные бонусы, отмена оффера, зарубежные офферы (BR-15, BR-14); реестры: нормальный, с остатком округления, большой (NFR-02); пары «ожидаемая / фактическая сумма» (BR-27); корректировки: в день и задним числом (BR-30, BR-35).

### 7.4 Критерии приёмки

AC-01…AC-04 — см. раздел G. У BR-04, BR-05, BR-14, BR-15 отдельных критериев приёмки в BRD нет.

# Сценарии проверки скилла

## Содержание

- Два разных набора
- Поздний сценарий для сессионных скиллов
- Сценарии выдачи: формат и требования
- Триггерные запросы: формат и требования
- Базовая линия
- Прогон без субагентов
- Когда сценарии пора менять

---

## Два разных набора

Скилл может отказать двумя независимыми способами, и проверяются они разными наборами.

| Набор | Что проверяет | Что чинится при провале | Минимум |
|---|---|---|---|
| Сценарии выдачи | делает ли скилл то, что обещает | тело `SKILL.md`, ресурсы, скрипты | 3 сценария, для сессионного — плюс поздний |
| Триггерные запросы | вызывается ли скилл там, где нужен | только `description` | 20 запросов, из них 10 отрицательных |

Смешивать их нельзя: скилл с отличной выдачей и плохим описанием не запускается ни разу,
и по сценариям выдачи это невидимо.

---

## Сценарии выдачи: формат и требования

Файл `evals/evals.json`:

```json
{
  "skill_name": "имя-скилла",
  "evals": [
    {
      "id": 1,
      "prompt": "реальная формулировка задачи, как её напишет пользователь",
      "expected_behavior": [
        "проверяемое утверждение о результате",
        "ещё одно проверяемое утверждение"
      ],
      "files": []
    },
    {
      "id": 4,
      "phase": "late",
      "prompt": "последняя реплика, на которую должно сработать правило",
      "expected_behavior": ["правило сработало в конце сессии, а не только в начале"],
      "files": ["fixtures/late-session.md"]
    }
  ]
}
```

**Задача берётся настоящая.** «Проверь этот скилл» — не сценарий. Сценарий — задача
с материалом, ограничениями и контекстом, на которой скилл реально применяли.

**Ожидания формулируются проверяемо.** Утверждение годится, если два человека независимо
дадут по нему один и тот же ответ «да» или «нет».

| Годится | Не годится |
|---|---|
| «В отчёте у каждого пункта названа цена нарушения» | «Отчёт качественный» |
| «Приоритеты расставлены по цене, а не по трудоёмкости» | «Приоритеты разумные» |
| «Перенесённый текст совпадает с исходным дословно» | «Перенос сделан аккуратно» |

**Сессионному скиллу нужен поздний сценарий.** Один из сценариев проверяет поведение
не на первых репликах, а в конце длинной сессии, и помечается `"phase": "late"`. Он
отвечает на вопрос, исполняются ли правила тела на сотом сообщении или растворились
в разговоре. Без него класс `session` не даёт права на порог 8000: экономия токенов
проверяется валидатором, а сохранность поведения — только этим сценарием.

**Поздний сценарий содержит сессию, а не её описание.** Транскрипт длинной сессии кладётся
в `files` (`evals/fixtures/…`), в `prompt` — последняя реплика, на которую должно сработать
правило. Описание вроде «интервью идёт шестьдесят реплик, пройдены блоки 1–9» проверяет, узнаёт
ли агент правило, но не разбавление внимания: в коротком контексте правилам не с чем
конкурировать, и сценарий проходит у любой версии. Такой сценарий валидатор отмечает
предупреждением. Транскрипт — синтетический или обезличенный: боевой содержит данные заказчика.

**Три сценария покрывают разное.** Типовой случай, пограничный случай и случай, на котором
скилл раньше ошибался. Три вариации одной задачи не проверяют ничего.

## Триггерные запросы: формат и требования

```json
[
  {"query": "формулировка пользователя", "should_trigger": true},
  {"query": "другая формулировка", "should_trigger": false}
]
```

Запросы пишутся так, как их пишет человек: со своими словами, сокращениями, опечатками,
кусками контекста («у меня скилл на 500 строк, всё в одном файле, хочу разнести»).
Абстрактные формулировки вроде «проверь файл» не проверяют ничего.

**Ценность отрицательных запросов — в близких промахах.** Отрицательный пример,
не имеющий со скиллом ничего общего, проходит всегда и не измеряет качество описания.

| Хороший отрицательный пример | Почему хороший |
|---|---|
| «Напиши скилл для разбора выгрузок из CRM» | создание с нуля — соседняя задача, слова те же |
| «Проверь мой markdown-документ на структуру» | «проверь» + документ, но предмет другой |
| «Почему Claude не читает мой файл из папки?» | похоже на жалобу про навигацию, но это вопрос про среду |

**Половина положительных запросов — без ключевых слов скилла.** Пользователь скажет
«скилл жрёт контекст», а не «проведи аудит соответствия стандарту». Если описание ловит
только собственную терминологию, оно не работает.

## Базовая линия

Та же задача, прогнанная без скилла. Нужна для двух разных выводов:

- **до правок** — фиксирует текущее поведение, чтобы после переработки увидеть регресс;
- **при создании** — отвечает на вопрос, нужен ли скилл вообще. Скилл, результат которого
  не отличается от прогона без него, стоит контекста и не даёт ничего.

Базовая линия сохраняется вместе с результатами, а не пересказывается по памяти.

---

## Прогон без субагентов

В интерфейсе чата параллельный запуск недоступен, поэтому сценарии прогоняются по одному:
прочитать `SKILL.md`, выполнить задачу по нему, сохранить результат. Это слабее независимой
проверки — тот, кто писал скилл, прогоняет его же, — и потому результат обязательно
показывается человеку, а не оценивается самостоятельно.

Ограничение называется в отчёте прямо. Прогон, выданный за независимую проверку,
хуже отсутствия прогона: он создаёт ложную уверенность.

---

## Когда сценарии пора менять

Сценарий, который проходит всегда, независимо от состояния скилла, ничего не измеряет
и заменяется. То же с отрицательным запросом, который никогда не срабатывает.

Сценарии расширяются, когда скилл ошибся на реальной задаче: эта задача добавляется
в набор до починки, а не после.

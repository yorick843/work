# Стандарт написания скиллов

Эталон, к которому приводятся все наши скиллы — и новые, и уже написанные.
Опирается на спецификацию Agent Skills (agentskills.io), руководство Anthropic по
авторингу скиллов и на разбор наших пяти действующих скиллов.

Механическая часть стандарта проверяется скриптом `check-skill.py`:

```bash
python3 check-skill.py <путь-к-скиллу> [<ещё-скилл> ...]
```

При нескольких путях он дополнительно сравнивает скиллы между собой — ловит конкуренцию
описаний и разошедшиеся копии общих файлов. Содержательная часть проверяется вручную
по чек-листу раздела 15.

## 1. Принцип, из которого выводится всё остальное

**Контекст — общий ресурс.** Скилл делит окно с системным промптом, историей диалога,
метаданными всех остальных установленных скиллов и собственно запросом пользователя.
Каждый токен скилла отнимает место у рассуждения над задачей.

Из этого выводятся бюджеты (раздел 3), структура папок (раздел 5) и правило размещения
(раздел 4). Если при написании возникает спор «оставить в теле или вынести» — спор решается
этим принципом, а не удобством автора.

**Второй принцип: модель уже умная.** В скилл пишется только то, чего модель не знает:
ваш домен, ваши договорённости, ваши форматы, ваши грабли. Не пишется: объяснение, что такое
PDF, зачем нужны требования, как работает markdown. Тест на каждый абзац — «модель справится
без этого?». Если да — абзац удаляется.

Эти два принципа противоречат привычке писать документ для человека. Скилл — не документация.
README для человека, SKILL.md для модели, и это разные тексты.

## 2. Инварианты формата

Нарушение любой строки таблицы означает, что скилл либо не загрузится, либо загрузится
не везде. Проверяется скриптом.

| Требование | Значение | Что ломается при нарушении |
|---|---|---|
| Папка с `SKILL.md` в корне | обязательно | скилл не распознаётся |
| Frontmatter с первого байта, между `---` | обязательно | метаданные не читаются |
| `name` | ≤ 64 симв., только `a-z`, `0-9`, дефис; без крайних и сдвоенных дефисов | скилл не проходит валидацию |
| `name` == имя папки | точное совпадение | скилл не загрузится |
| `name` без слов `anthropic`, `claude` | зарезервировано | отказ валидации |
| `description` | непустой, ≤ 1024 симв. | скилл не сработает или не загрузится |
| Угловые скобки в frontmatter | запрещены | риск инъекции в системный промпт |
| Опциональные поля | только `license`, `compatibility` (≤500), `metadata`, `allowed-tools` | часть рантаймов отвергает скилл с посторонними полями |
| Пути | только прямые слэши | обратные слэши ломаются вне Windows |
| `allowed-tools` | экспериментальное поле | поддержка различается между платформами — не закладываться |

Формат — открытый стандарт, его понимают более двух десятков платформ помимо Claude.
Поэтому дисциплина по этой таблице — не бюрократия, а переносимость: скилл, написанный
по спецификации, работает и в другом агенте без переделки.

## 3. Три уровня загрузки и бюджеты

| Уровень | Что в нём | Когда попадает в контекст | Бюджет | Цена ошибки |
|---|---|---|---|---|
| Метаданные | `name` + `description` | всегда, для всех установленных скиллов | ~100 токенов на скилл | платится постоянно и за все скиллы сразу |
| Тело `SKILL.md` | инструкции, порядок работы, карта ресурсов | при срабатывании скилла, целиком | < 5000 токенов для одноразового скилла, < 8000 для сессионного | платится при каждом запуске скилла |
| Ресурсы | `references/`, `assets/` | только когда модель их прочитает | не ограничен | ноль до чтения |
| Скрипты | `scripts/` | исполняются, в контекст идёт только вывод | не ограничен | ноль, если запускать, а не читать |

**Русский язык дороже.** Кириллица токенизируется примерно вдвое хуже латиницы: тот же
смысл стоит примерно вдвое больше токенов. Практическое следствие: у русскоязычного скилла
порог 5000 токенов наступает раньше, чем порог 500 строк, и ориентироваться надо на токены.
Порог в строках — вторичный индикатор.

Именно здесь провалился `analytical-dossier-page`: 543 строки выглядят почти нормой,
а по токенам это ~26 000 — пятикратное превышение, которое оплачивается при каждом
срабатывании скилла, даже когда нужен один его раздел.

### Класс скилла: одноразовый и сессионный

Тело грузится один раз за сессию. Поэтому одна и та же величина стоит по-разному:

| Класс | Что делает | Длина сессии | Порог тела |
|---|---|---|---|
| Одноразовый (по умолчанию) | отрабатывает задачу и завершается | единицы сообщений | 5000 токенов |
| Сессионный | ведёт многошаговый диалог, состояние копится в переписке | десятки и сотни сообщений | 8000 токенов |

Признак сессионного класса — не объём скилла, а то, что он управляет длинным диалогом:
интервью, пошаговое сопровождение, игра, разбор с итерациями. Скилл, который просто вырос,
сессионным не становится.

Класс объявляется явно: `metadata.type: session`. По размеру он не выводится — иначе любое
превышение будет задним числом объявлено особенностью жанра.

**Допуск в класс требует всех трёх условий:**

1. **Класс объявлен** в `metadata.type`.
2. **Ветки всё равно вынесены.** В теле не осталось блоков, которые нужны в меньшинстве
   сессий и выбираются явным решением. Класс поднимает порог, а не отменяет разбиение.
3. **Есть сценарий, проверяющий поведение в конце длинной сессии** — помечается
   `"phase": "late"` в `evals/evals.json` и содержит саму сессию: транскрипт в `files`, а не
   её описание в промпте.

Третье условие — не бюрократия. У длинного тела есть вторая цена, не токенная: разбавление
внимания. Два десятка правил конкурируют за исполнение с самим разговором, и на сотом
сообщении часть из них перестаёт срабатывать. Токены при этом сэкономлены, а скилл не
работает. Проверяется это только прогоном на длинной сессии, и ничем другим.

8000 — потолок, а не цель. Класс не отменяет ни одного другого требования стандарта.

## 4. Правило размещения: куда девать конкретный кусок текста

**Место текста определяется частотой обращения к нему, а не темой.** Это главная ошибка
при раскладке: файлы режут по темам, «чтобы красиво», а резать надо по тому, в каком проценте
запусков текст реально нужен.

| Вопрос про кусок текста | Слой | Проверка |
|---|---|---|
| Нужен почти в каждом запуске и определяет поведение | тело `SKILL.md` | без него скилл ведёт себя неправильно всегда |
| Нужен в части запусков, выбирается ветвлением | `references/` | есть запуск, где он не нужен вовсе |
| Детерминированная повторяемая операция | `scripts/` | результат не зависит от суждения модели |
| Попадает в результат как есть | `assets/` | файл копируется, а не читается |
| Нужен человеку, не модели | `README.md`, `CHANGELOG.md` | модель может никогда его не открыть |
| Нужен для проверки самого скилла | `evals/` | не участвует в работе скилла |

**Порог выделения.** Блок выносится в `references/`, если одновременно: занимает ≥ 40 строк
**и** нужен не в каждом запуске. Мелкие блоки не выносятся — навигация к файлу обойдётся
дороже самого содержимого, а модель может до него не дойти.

**Обратное правило.** Если файл в `references/` читается при каждом запуске — он должен быть
в теле. Постоянно читаемая ссылка — это лишний шаг и лишний риск, что модель прочитает файл
частично.

## 5. Какие области знаний выделять в подпапки

Шесть осей декомпозиции. Ось выбирается по природе знания, а не по объёму: объём определяет
только, выносить ли вообще (раздел 4).

| Ось | Признак, что резать нужно именно так | Что кладём в файл | Шаблон имени |
|---|---|---|---|
| **Вариант предметной области** | ветки взаимоисключающие, в одном запуске нужна ровно одна | всё знание про один домен/рынок/фреймворк | `references/<вариант>.md`, при 4+ вариантах — `references/domains/<вариант>.md` |
| **Фаза рабочего процесса** | знание нужно на одном шаге из нескольких и не нужно на остальных | материал одного шага целиком | `references/question-bank.md`, `references/triage.md` |
| **Канал или формат выдачи** | результат один, а способ доставки разный | процедура доставки в один канал | `references/channels/<канал>.md` |
| **Шаблон результата** | эталон, который заполняется и отдаётся | скелет с плейсхолдерами | `references/output-template.md` |
| **Эталонный разбор** | длинный сквозной пример на реальном материале | один прогон от входа до выдачи | `references/worked-example.md` |
| **Редкие случаи и глубина** | нужно в меньшинстве запусков, но там критично | пограничные случаи с признаками опознания | `references/edge-cases.md` |

Три правила, обязательных при любой оси:

**Один файл — одна ветка.** Модель читает файл целиком. Две несвязанные ветки в одном файле
означают, что половина прочитанного — балласт. Обратное тоже верно: одна ветка, размазанная
по трём файлам, будет прочитана частично.

**Ссылки — один уровень от `SKILL.md`.** Вложенность **папок** допустима: `references/styles/base.md`
нормально. Вложенность **ссылок** — нет: если файл упоминается только внутри другого
reference-файла, модель дочитает его частично или не дойдёт вовсе. Каждый файл пакета должен
быть достижим прямой ссылкой из тела `SKILL.md`.

**Оглавление в файлах длиннее 100 строк.** Модель часто просматривает длинный файл
частично. Оглавление в первых строках даёт ей карту, даже если прочитан только верх.

## 6. Итоговая структура скилла

```
skill-name/
├── SKILL.md            обязателен. Инструкции для модели. Корень пакета.
├── README.md           для человека: назначение, установка, версия, ограничения.
├── CHANGELOG.md        для человека: что менялось и почему.
├── references/         читается моделью по требованию
│   ├── domains/          варианты предметной области
│   ├── channels/         варианты доставки результата
│   ├── output-template.md
│   ├── worked-example.md
│   └── edge-cases.md
├── assets/             попадает в результат как есть: шаблоны, стили, шрифты, картинки
├── scripts/            исполняется, не читается
│   ├── <действие>.py     рабочие утилиты скилла
│   └── selftest.py       самопроверка согласованности скилла
└── evals/
    └── evals.json      сценарии проверки скилла
```

| Файл или папка | Обязателен | Кто использует | Когда | Назначение |
|---|---|---|---|---|
| `SKILL.md` | да | модель | при срабатывании, целиком | что делать, в каком порядке, куда идти дальше |
| `README.md` | для командных скиллов | человек | при установке и передаче | назначение, установка, версия, границы применимости |
| `CHANGELOG.md` | для скиллов старше одной итерации | человек | при разборе регресса | почему скилл стал таким |
| `references/` | по необходимости | модель | по ветке задачи | знание, нужное не всегда |
| `assets/` | по необходимости | результат | при сборке выдачи | то, что не читают, а вставляют |
| `scripts/` | по необходимости | среда | по шагу процесса | детерминированные операции и проверки |
| `evals/` | да, начиная со второй версии | человек и прогоны | при изменении скилла | доказательство, что скилл работает |

Пустые папки не создаются. Структура растёт от одного файла: скилл на 200 строк без ветвлений —
это `SKILL.md` и ничего больше, и это нормальная зрелая форма, а не недоделка.

### Карта состава и данных: ведётся вместе с пакетом

Любой скилл больше одного файла имеет в `README.md` раздел `## Состав` — карту того, из чего
пакет состоит и какие данные он читает и создаёт. Причина: набор файлов меняется быстрее, чем
его помнят; без карты человек не знает, что можно удалить, что — переносить вместе с пакетом, а
что содержит данные проекта (фикстуры, образцы), которые нельзя отдавать за пределы команды.

| Что | Правило |
|---|---|
| Форма | таблица `Путь \| Назначение`; пути в обратных кавычках; папка записывается со слэшем (`references/core/`) и покрывает всё внутри |
| Полнота | каждый файл пакета, кроме `SKILL.md`, `README.md`, `CHANGELOG.md`, описан строкой или покрыт папкой; пути, которых нет на диске, из карты удаляются |
| Данные | отдельной строкой или подразделом: что скилл читает на входе, что создаёт на выходе (имя и формат файла), что в пакете содержит данные проекта и персональные данные |
| Момент обновления | в той же правке, что добавляет, переименовывает или удаляет файл; запись в `CHANGELOG.md` называет изменение карты |
| Что не входит | правила работы: они живут только в `SKILL.md`, карта лишь указывает, где что лежит |

Расхождение карты и пакета ловит `check-skill.py` (предупреждение). Карта описывает файлы, но не
заменяет раздел «Ресурсы» в `SKILL.md`: тот говорит модели, когда файл открывать, эта — человеку,
зачем файл существует.

## 7. Именование файлов

| Объект | Шаблон | Хорошо | Плохо |
|---|---|---|---|
| Скилл (папка и `name`) | kebab-case, латиница, герундий или именная группа, домен в имени | `fintech-career-advisor`, `analytical-dossier-page`, `processing-pdfs` | `helper`, `utils`, `my-skill`, `analytics2` |
| Reference | существительное-предмет, kebab-case, `.md`; имя называет ветку | `question-bank.md`, `domain-profiles.md`, `channels/confluence.md` | `doc2.md`, `extra.md`, `notes.md`, `part1.md` |
| Script | глагол действия | `check-page.py`, `fill-form.py`, `selftest.py` | `utils.py`, `script.py`, `main.py` |
| Asset | имя артефакта как он поедет в результат | `base-archive.css`, `letterhead.docx` | `style1.css`, `template_final.docx` |

Правила поверх таблицы:

- **Имя называет содержимое, а не порядок.** `part1.md` и `doc2.md` не говорят модели ничего;
  выбирать между ними она будет случайно.
- **Версия не живёт в имени.** Никаких `-v2`, `-new`, `-final`, `-md`. Версия — в
  `metadata.version` и `CHANGELOG.md`. Имя скилла стабильно, иначе ломаются ссылки и установки.
- **Латиница даже в русскоязычных скиллах.** Имена файлов — часть путей и команд; кириллица
  в путях создаёт проблемы при упаковке и переносе. Содержимое при этом пишется на русском.
- **Имя reference-файла = формулировка ветки в `SKILL.md`.** Если в теле написано «для
  Confluence см. …», файл называется `channels/confluence.md`, а не `publishing.md`. Совпадение
  формулировки и имени — то, по чему модель находит нужный файл с первой попытки.

## 8. Канон тела SKILL.md

Порядок разделов. Отсутствующие разделы допустимы, перестановка — нет: порядок повторяет
последовательность, в которой модель принимает решения.

| # | Раздел | Что содержит | Жёсткое требование |
|---|---|---|---|
| 1 | `# Название` + одна фраза | что скилл делает | одна фраза, не абзац |
| 2 | `## Когда применять, а когда нет` | границы, включая явные «не применять, если…» | обязателен раздел «когда не применять» |
| 3 | `## Порядок работы` | пронумерованные шаги | шаги нумерованные, копируемые как чек-лист |
| 4 | `## Ресурсы` | карта файлов пакета | у каждого файла глагол: «прочитай» или «запусти» |
| 5 | предметное ядро | правила, критерии, форматы — то, чего модель не знает | ноль объяснений общеизвестного |
| 6 | `## Чего не делать` | антипаттерны | у каждого — признак опознания, а не только запрет |
| 7 | `## Проверка перед выдачей` | чек-лист приёмки результата | пункты проверяемые, а не «убедись в качестве» |
| 8 | `## Что здесь может устареть` | утверждение / на чём стоит / что отменит | таблица, а не проза |

Требования к тексту тела:

**Каждое требование сопровождается причиной.** Модель хорошо исполняет то, смысл чего
понимает, и плохо — то, что предъявлено как голый запрет. Капслочные `ВСЕГДА` и `НИКОГДА` —
маркер того, что автор не нашёл причину. Допустимо не более трёх капслоков на скилл, и только
там, где цена ошибки необратима.

**Единая терминология.** Один термин на одно понятие по всему скиллу. Смесь «поле / атрибут /
элемент / реквизит» заставляет модель гадать, одно это или разное.

**Ноль дат и «сейчас».** Формулировки вида «до августа 2025 использовать старый API» протухают
молча. Устаревшее выносится в отдельный раздел «старые практики» и помечается как устаревшее,
а не датируется в основном тексте.

**Императив.** «Проверь», «собери», «прочитай» — не «следует проверить», не «рекомендуется».

## 9. Description — единственный механизм срабатывания

`description` — единственное, что модель видит до того, как решит открыть скилл. Тело скилла
на срабатывание не влияет никак. Плохое описание означает, что отличный скилл не запустится.

**Формула:**

```
[что делает: 1–2 предложения] +
[когда применять: конкретные формулировки, которыми пользователь опишет задачу] +
[пограничные случаи: когда применять, хотя не очевидно / когда не применять]
```

| Правило | Причина |
|---|---|
| Третье лицо | описание вставляется в системный промпт; «я помогу» ломает согласование |
| Язык пользователя | русскоязычная команда формулирует запросы по-русски — триггеры должны быть русскими |
| Синонимы и разговорные формулировки | пользователь скажет «собери сводку», а не «сгенерируй аналитическое досье» |
| Подталкивающая формулировка | модели чаще **недо**-срабатывают, чем пере-срабатывают; «использовать всегда, когда…» оправдано |
| Рабочий диапазон 300–800 символов | ниже — не хватает триггеров; выше — нет запаса до лимита 1024 и растёт постоянная плата за метаданные |
| Явная граница с соседним скиллом | при похожих описаниях выбор между скиллами становится случайным |

**Конкуренция скиллов — отдельный риск.** Если два скилла в портфеле решают близкие задачи,
в описании каждого должна стоять разделительная фраза: «…не использовать, если нужен <X> —
для этого <имя другого скилла>». Без неё срабатывание распределяется непредсказуемо, и
диагностировать это трудно: оба скилла по отдельности выглядят исправными.

## 10. Степени свободы

Степень детализации инструкции определяется хрупкостью операции, а не важностью темы.

| Тип участка | Признак | Форма инструкции | Пример |
|---|---|---|---|
| Узкий мост | шаг хрупкий, порядок критичен, ошибка необратима | точная команда, без вариаций, с запретом на модификацию | «Запусти ровно `python scripts/migrate.py --verify --backup`, флаги не менять» |
| Средний участок | есть предпочтительный путь, вариации допустимы | шаблон или псевдокод с параметрами | «Используй этот шаблон отчёта, адаптируй разделы под тип анализа» |
| Открытое поле | много верных путей, выбор зависит от контекста | направление и критерии качества | «Проверь структуру, найди краевые случаи, предложи улучшения читаемости» |

Ошибка в обе стороны стоит одинаково: жёсткая инструкция на открытом поле мешает модели
работать, мягкая на узком мосту — ломает результат.

## 11. Скрипты

**Когда скрипт обязателен.** Операция детерминирована, повторяется и проверяема. Отдельный
сильный признак: если в нескольких прогонах модель писала один и тот же вспомогательный
скрипт — он должен лежать в `scripts/`. Готовый скрипт надёжнее сгенерированного, не тратит
токены и даёт одинаковый результат каждый раз.

**Требования к скриптам:**

| Требование | Формулировка |
|---|---|
| Решать, а не откладывать | ошибки обрабатываются внутри скрипта, а не «пусть модель разберётся» |
| Внятные ошибки | «Поле `signature_date` не найдено. Доступные поля: …» вместо трассировки |
| Никаких магических констант | у каждого числа комментарий с обоснованием; если автор не знает верного значения, модель тем более не узнает |
| Явный глагол в `SKILL.md` | «запусти `check-page.py`» и «прочитай `check-page.py` как справку» — разные инструкции, различать обязательно |
| Объявленные зависимости | в среде API нет сети и установки пакетов; в claude.ai установка возможна |
| Прямые слэши | переносимость |

**`selftest.py` — канон.** Скрипт, проверяющий внутреннюю согласованность самого скилла:
сходятся ли счётчики, живы ли ссылки, соответствует ли эталонный разбор текущим правилам.
Практика взята из `analytical-dossier-page`, где она уже ловила расхождения между `SKILL.md`
и разбором, и распространяется на все скиллы со связанными файлами. Скилл без внутренних
зависимостей в нём не нуждается.

## 12. Проверяемость: evals

Скилл без проверки — гипотеза. Норма минимума:

| Что | Объём | Зачем |
|---|---|---|
| Сценарии выдачи | не менее 3 реалистичных задач | проверяют, что скилл делает то, что обещает |
| Запросы на срабатывание | 20: 10 должны сработать, 10 не должны | проверяют `description` |
| Базовая линия | те же задачи без скилла | скилл, не меняющий результат, не нужен |

Ценность запросов на срабатывание — в близких промахах. «Напиши функцию» как отрицательный
пример для скилла про досье не проверяет ничего. Проверяет — «собери мне таблицу по инцидентам
за квартал», где скилл может сработать ошибочно.

Формат `evals/evals.json`:

```json
{
  "skill_name": "analytical-dossier-page",
  "evals": [
    {
      "id": 1,
      "prompt": "реальная формулировка задачи, как её напишет пользователь",
      "expected_behavior": [
        "проверяемое утверждение о результате",
        "ещё одно проверяемое утверждение"
      ],
      "files": []
    }
  ]
}
```

Ожидания формулируются проверяемо: «в выдаче есть раздел о пробелах в данных» — да;
«выдача качественная» — нет.

## 13. Версия, изменения, поставка

| Артефакт | Правило |
|---|---|
| Версия | `metadata.version` в frontmatter — единственный машинно-читаемый источник. Дублирование версии в README допустимо, но README не является источником |
| `CHANGELOG.md` | одна запись на одну содержательную правку, с указанием, что изменилось и почему. Старые записи сворачиваются в сводку по мере роста файла |
| `README.md` | для человека. Правила работы туда не дублируются: две копии правил расходятся, и никто не знает, какая главная; раздел `## Состав` — карта файлов и данных пакета, обновляется вместе с ним (раздел 6) |
| Пакет | zip или `.skill`, внутри — папка скилла с `SKILL.md` в её корне |
| Чистка перед упаковкой | `__pycache__`, `.DS_Store`, `*.pyc`, временные файлы |
| Секреты | в скилл не кладутся: пакет переносится целиком, включая всё, что в нём лежит |
| Доверие | скилл из непроверенного источника проверяется целиком перед установкой — он несёт инструкции и исполняемый код |

Разумный ориентир по объёму: `CHANGELOG.md` не должен превосходить `SKILL.md`. Если превзошёл —
историю пора сворачивать, потому что её перестают читать.

## 14. Антипаттерны

| Антипаттерн | Признак опознания | Чем заменить |
|---|---|---|
| Всё в теле | тело сверх порога своего класса; в теле есть разделы, нужные в меньшинстве запусков | вынести ветки в `references/` по осям раздела 5 |
| Класс вместо разбиения | `metadata.type: session` объявлен, а ветки из тела не вынесены | сначала вынос, класс — только для остатка |

| Клон вместо ветки | два скилла с почти одинаковым описанием, отличающиеся одним аспектом | один скилл, аспект — ветка в `references/` |
| Устаревшая карта файлов | в `README.md` перечислены файлы, которых нет, или нет файлов, которые есть | обновлять `## Состав` в той же правке, что меняет набор файлов |
| README как вторая инструкция | правила описаны и в `SKILL.md`, и в `README.md` | правила только в `SKILL.md`, README — про установку и границы |
| Капслочный императив | больше трёх `ВСЕГДА`/`НИКОГДА` | сформулировать причину; если причины нет, требование сомнительно |
| Даты в основном тексте | «с августа 2025», «на текущий момент» | раздел «старые практики» + раздел «что может устареть» |
| Объяснение общеизвестного | абзац, объясняющий, что такое PDF или зачем нужны требования | удалить |
| Имя-заглушка | `doc2.md`, `utils.py`, `helpers/` | имя по содержимому |
| Скрипт, который падает | нет обработки ошибок, расчёт на то, что модель починит | обработка внутри скрипта |
| Меню вариантов | «можно использовать A, или B, или C» | один вариант по умолчанию + условие, когда переходить на другой |

## 15. Приёмочный чек-лист

Пункты, помеченные `[скрипт]`, проверяет `check-skill.py`. Остальные — человек.

**Формат**
1. `[скрипт]` `SKILL.md` в корне, frontmatter с первого байта
2. `[скрипт]` `name` соответствует правилам и совпадает с именем папки
3. `[скрипт]` `description` непустой, ≤ 1024, без угловых скобок
4. `[скрипт]` посторонних полей frontmatter нет
5. `[скрипт]` `metadata.version` и `metadata.updated` заполнены

**Контекст**
6. `[скрипт]` тело в пределах порога своего класса: 5000 токенов, для сессионного 8000
7. `[скрипт]` класс объявлен в `metadata.type`, если скилл сессионный
8. `[скрипт]` тело < 500 строк
9. В теле нет разделов, нужных в меньшинстве запусков — в том числе у сессионного скилла
10. Нет объяснений того, что модель знает и так

**Навигация**
11. `[скрипт]` все ссылки из `SKILL.md` ведут на существующие файлы
12. `[скрипт]` нет файлов, достижимых только через другой reference-файл
13. `[скрипт]` нет файлов, не упомянутых в `SKILL.md`
14. `[скрипт]` reference-файлы длиннее 100 строк имеют оглавление
15. Имя каждого файла совпадает с формулировкой ветки в теле
16. У каждого ресурса в разделе «Ресурсы» стоит глагол «прочитай» или «запусти»

**Срабатывание**
17. Описание содержит и «что делает», и «когда применять»
18. Триггеры сформулированы на языке пользователя
19. `[скрипт]` описание не конкурирует с описанием соседнего скилла
20. Для соседних скиллов есть явная разделительная фраза

**Содержание**
21. Есть раздел «когда не применять»
22. Порядок работы пронумерован и копируется как чек-лист
23. У каждого требования есть причина, включая числовые пороги
24. `[скрипт]` не больше трёх капслочных императивов
25. Единая терминология
26. Нет дат и «сейчас» в основном тексте
27. Есть раздел «что здесь может устареть»

**Скрипты**
28. Ошибки обрабатываются внутри, сообщения называют конкретную причину
29. Все константы обоснованы комментарием
30. `selftest.py` есть и проходит — для скиллов со связанными файлами

**Проверяемость и поставка**
31. `[скрипт]` есть `evals/` не менее чем с тремя сценариями
32. `[скрипт]` у сессионного скилла есть сценарий с `"phase": "late"`, содержащий транскрипт сессии
33. Прогон с базовой линией показывает разницу
34. `[скрипт]` в пакете нет служебного мусора (`__pycache__`, `.DS_Store`, `*.pyc`)
35. Секретов и персональных данных в пакете нет
36. `[скрипт]` в `README.md` есть раздел `## Состав`; каждый файл пакета описан, несуществующих путей нет
37. В карте названы данные, которые скилл читает и создаёт, и фикстуры с данными проекта

## 16. Порядок приведения существующего скилла к стандарту

Порядок операций важнее скорости: смешанные правки не диагностируются.

1. **Зафиксировать базовую линию.** Прогнать `check-skill.py` и сохранить вывод.
   Прогнать 3 сценария на текущей версии и сохранить результаты.
2. **Написать evals, если их нет.** До правок, а не после: иначе не с чем сравнивать.
3. **Перенос без редактуры.** Вынести ветки в `references/`, не меняя ни одного слова
   переносимого текста. Это отдельный коммит и отдельный прогон. Если смешать перенос
   с правкой содержания, регресс невозможно будет отнести к причине.
4. **Прогнать evals после переноса.** Результат должен совпасть с базовой линией.
   Несовпадение означает, что модель перестала находить перенесённое — чинить навигацию,
   а не содержание.
5. **Содержательные правки — по одной**, каждая со своим прогоном и записью в `CHANGELOG.md`.
6. **Пересобрать пакет и обновить `metadata.version`.**

Правило: одна правка — один прогон.

## 17. Что здесь может устареть

| Утверждение | На чём стоит | Что его отменит |
|---|---|---|
| Лимиты 64 / 1024 / 500 символов | текущая редакция спецификации Agent Skills | новая ревизия спецификации |
| Пороги 5000 и 8000 токенов на тело | рекомендация, а не проверка рантайма | удешевление контекста или рост окна делает пороги мягче |
| Разделение на одноразовые и сессионные скиллы | разная амортизация тела и наблюдаемое разбавление внимания в длинных сессиях | модели, одинаково исполняющие правила на первом и сотом сообщении, сделают класс ненужным |
| Набор папок `references` / `scripts` / `assets` | конвенция спецификации | появление новых канонических папок; `evals/` уже полуофициальна |
| `allowed-tools` — экспериментальное поле | текущий статус в спецификации | стабилизация поля или его отмена |
| Оценка «кириллица вдвое дороже» | свойство текущих токенизаторов | смена токенизатора в новых моделях |
| «Модель уже умная, объяснять не надо» | верно для моделей уровня Sonnet и выше | на младших моделях требуется больше явности — проверять на той модели, которой пользуетесь |
| Правило «ссылки один уровень» | наблюдаемое поведение при частичном чтении файлов | изменение стратегии чтения файлов агентом |
| Оценка токенов в `check-skill.py` | эвристика по доле кириллицы, точность ±20% | появление точного счётчика токенов в среде |
